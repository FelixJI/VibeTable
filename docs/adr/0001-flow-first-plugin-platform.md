# ADR 0001：采用 Flow-first 插件平台

- 状态：已废弃（由 PocketBase 退出架构取代）
- 日期：2026-07-20
- 决策者：VibeTable 产品与工程

> 2026-07-24：VibeTable 已移除 Directus/Flow-first 生产路径。本 ADR 仅保留为历史决策记录；现行边界见
> [`docs/research/2026-07-24-directus-exit-architecture.md`](../research/2026-07-24-directus-exit-architecture.md)。

## 背景

VibeTable 需要用按钮、表单、弹窗、自定义面板和批量任务把数据自动化能力产品化。Directus 已经提供 Flow、触发器、Operation 和服务端数据访问；如果插件再提供一套自由编排引擎，Flow 与插件会同时承担业务流程、写入、重试和生命周期管理，形成重复能力与模糊边界。

同时，纯 Flow 无法完整承担桌面交互、本地文件、客户端计算、主题一致性、离线分发和插件中心体验。系统仍需要一个可安装的扩展层。

## 决策

VibeTable 采用 Flow-first 插件平台：

- Flow 能表达的业务编排、服务端数据操作、Webhook、定时和事件触发放在 Directus Flow 中。
- 插件负责动作入口、标准或自定义界面、本地能力、包管理、项目级配置、Flow 绑定和执行呈现。
- 每个 `flow` 或 `hybrid` 动作只绑定一个入口 Flow；子流程编排留在 Directus 内部。
- 插件可以提供受控的客户端扩展逻辑，但不开放通用工作流编排、任意 RPC 或插件间依赖。
- Flow 分为由 VibeTable 维护的托管 Flow 和用户维护的外部 Flow，两者拥有不同生命周期。

## 后果

### 正面

- 复用 Directus 的编排、权限和触发器能力，减少重复实现。
- 插件的价值集中在产品化、桌面交互和 Flow 缺失能力，职责更稳定。
- Flow 仍可在 Directus 中独立查看和调试，外部 Flow 也能被现有用户复用。
- 插件动作有统一任务、风险、确认和审计体验。

### 代价

- 插件安装器需要处理 Flow 创建、逻辑 ID 到 UUID 映射、升级、偏离与回滚。
- 交互式写入 Flow 需要 VibeTable 提供公共确认/进度 Operation 和运行时交互桥。
- 客户端与 Directus 之间必须维护版本化输入输出契约。
- 部分纯客户端能力仍需要 Web Worker，系统不能只实现 Flow 调用按钮。

## 被否决的方案

### 仅使用 Directus Flow

无法提供完整桌面交互、本地文件与计算、离线插件分发、主题受控自定义界面和统一插件中心。

### 插件内置独立工作流引擎

会与 Flow 重复，导致同一业务逻辑在两套编排模型、两套错误语义和两套生命周期之间分裂。

### 首版建设对抗恶意插件的高强度沙箱

当前产品是可信单用户工具，投入与复杂度不匹配。首版只保留稳定性隔离、关闭式宿主 API、独立禁网策略和权限声明，不承诺抵御恶意插件。

## 复审条件

出现以下任一情况时复审本决策：需要运行第三方不可信插件；需要插件独立于 Directus 工作；需要多人审批和重启后恢复；或 Directus Flow 不再是产品的主要服务端自动化能力。
